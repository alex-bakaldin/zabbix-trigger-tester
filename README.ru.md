# trigger-tester

[English](README.md) | Русский

Утилита проверяет триггер Zabbix 7.0+ на исторических данных: берёт выражение
триггера через API (или произвольное выражение из командной строки), находит
айтемы, выгружает их историю (и тренды, если нужны) за указанный период и
прогоняет выражение в каждой точке времени так, как это делал бы сервер, с его
машиной состояний (основное и восстановительное выражения, UNKNOWN).
Результат — хронология смен состояния OK/PROBLEM, сводка и, по желанию,
сравнение с реальными событиями сервера.

Движок вычислений — **собственный C-код сервера Zabbix**, собранный в небольшую
разделяемую библиотеку (`native/`), поэтому операторы, функции и граничные
случаи ведут себя ровно как на сервере. Чистая Python-реализация, сверенная с
нативной функция за функцией, служит запасным вариантом.

Утилита только читает данные: `apiinfo.version`, `trigger.get`, `item.get`,
`history.get`, `trend.get`, `event.get`, а также `user.login`/`user.logout`,
если вместо API-токена используется пароль.

## Зачем

Единственный способ проверить триггер в Zabbix — дождаться его срабатывания.
Кнопка «Тест» во фронтенде лишь считает операторы над числами, которые вы
вводите руками. Утилита за секунды отвечает на вопросы вроде «был бы
`min(/host/cpu,10m)>90` тише, чем `last()>90`, на прошлой неделе?», причём с
серверной семантикой.

## Установка

```bash
uv sync            # или: pip install -e .
uv run zbx-trigger-test --help
```

### Движок вычислений

```bash
native/fetch_sources.sh /tmp/zabbix-src      # клонирует закреплённый релиз Zabbix и собирает его библиотеки
ZABBIX_SRC=/tmp/zabbix-src native/build.sh   # -> native/libzbxtester.so
```

Нужны gcc, make, autoconf/automake, libtool, pkg-config и заголовки libpcre2.
Подробности, закреплённый релиз (`native/ZABBIX_TAG`) и переход на другой — в
[native/README.md](native/README.md).

Утилита умеет считать выражения двумя способами:

- **native** (рекомендуется): настоящий код сервера Zabbix (`libzbxeval`,
  `evalfunc.c`, `anomalystl.c`, `baseline.c`), собранный в
  `native/libzbxtester.so`. Операторы, трёхзначная логика UNKNOWN и все функции
  истории ведут себя байт в байт как на сервере. Библиотека ищется по
  переменной `ZBX_TRIGGER_TESTER_LIB`, рядом с пакетом и в `native/`.
- **python**: встроенная реализация на Python, сверенная с кодом сервера
  функция за функцией (включая порт `prediction.c` для `forecast`/`timeleft`).
  Работает без сборки. Дифференциальный тест `native/diff_test.py` гоняет
  одни и те же кейсы через оба движка и должен показывать 0 расхождений;
  при смене тега Zabbix его стоит перезапустить.

По умолчанию (`--engine auto`) используется native, если библиотека найдена,
иначе python с предупреждением. Какой движок работал, видно в шапке отчёта.

## Использование

```bash
export ZABBIX_URL=https://zabbix.example.com
export ZABBIX_TOKEN=xxxxxxxx           # API token (или --user/--password)

# последние сутки
zbx-trigger-test -t 23456

# заданный интервал, сравнение с реальными событиями, подробный вывод
zbx-trigger-test -t 23456 --from "2026-11-01 00:00" --till "2026-11-02 00:00" \
    --compare-events -v

# выражение, которого ещё нет в триггерах ("а что если"); элементы ищутся по /host/key
zbx-trigger-test --period 7d \
    --expression 'min(/srv1/system.cpu.util,10m)>{$CPU.MAX}' --macro '{$CPU.MAX}=85'

# ... с гистерезисом: закрытие по отдельному выражению восстановления
zbx-trigger-test --period 7d --expression 'last(/srv1/system.cpu.util)>90' \
    --recovery-expression 'last(/srv1/system.cpu.util)<70'

# JSON для дальнейшей визуализации
zbx-trigger-test -t 23456 --json result.json
```

Основные параметры:

| параметр | назначение |
|---|---|
| `--url`, `--token` / `--user` + `--password` | подключение (также `ZABBIX_URL`, `ZABBIX_TOKEN`, `ZABBIX_USER`, `ZABBIX_PASSWORD`); `--insecure` отключает проверку TLS |
| `-t/--trigger` | ID триггера; указывается либо `-t`, либо `--expression` |
| `--expression`, `--recovery-expression` | прогнать произвольное выражение вместо триггера (синтаксис Zabbix, ссылки `/host/key`). Выражение восстановления необязательно и переводит такой триггер в режим «recovery expression» |
| `--from`, `--till`, `--period` | период: ISO-дата, unix time, `now-1d`, `now/d`; по умолчанию последние `--period` (1d) до текущего момента |
| `--chunk`, `--page-size` | история выгружается окнами по времени (по умолчанию `6h`, `0` = весь период сразу) и страницами не более N строк (по умолчанию 10000) на один `history.get`, чтобы ни один запрос не был тяжёлым |
| `--step` | шаг «таймерных» вычислений; `auto` = 30s, если в одном из выражений есть `nodata()`, `date()/time()/now()/dayofweek()/dayofmonth()` или trend/baseline-функции (сдвиг времени сам по себе пересчёт на сервере не вызывает); `0` = выключить |
| `--macro {$NAME}=VALUE` | значение пользовательского макроса, который API не раскрыл |
| `--initial-state` | состояние в начале периода; `auto` берёт последнее событие до периода (для произвольного выражения — OK) |
| `--compare-events` | сравнить смоделированные смены состояния с событиями из Zabbix (только с `-t`) |
| `--engine` | `auto` / `native` / `python`, см. выше |
| `-v`, `-vv` | печатать каждое вычисление; `-vv` добавляет детали ошибок |
| `--tz` | таймзона отображения и округления `now/d`; для native-движка переключает TZ процесса, укажите зону сервера Zabbix |
| `--json FILE` | полный результат (каждое вычисление, значения функций) |
| `--debug` | логировать вызовы API и запросы данных нативного движка |

## Как это работает

1. С `-t`: `trigger.get` (с функциями, айтемами, хостами) и `trigger.get` с
   `expandExpression` — Zabbix сам раскрывает `{functionid}` и пользовательские
   макросы. С `--expression`: ссылки `/host/key` разрешаются через `item.get`.
2. Выражение разбирается в AST с приоритетами операторов Zabbix
   (`-`, `not`, `* /`, `+ -`, `< <= > >=`, `= <>`, `and`, `or`), суффиксами
   `K M G T s m h d w`, строками и макросами.
3. Для каждого айтема считается, сколько истории нужно *до* начала периода
   (окна `5m`, `#N`, сдвиги `:now-1h`), и история выгружается `history.get`
   окнами по времени и страницами по числу строк; для `trend*` и `baseline*` —
   `trend.get`.
4. Точки вычисления — каждое новое значение любого айтема триггера в периоде
   плюс сетка таймера для функций времени. Пересчёт в каждой точке повторяет
   серверную `zbx_evaluate_expressions()`:
   - сначала считается основное выражение; истинное даёт PROBLEM только если
     пересчёт вызван значением элемента из основного выражения или таймером
     этого выражения. Значение элемента, который есть лишь в выражении
     восстановления, или таймер, существующий только из-за него, PROBLEM
     поднять не могут (отчёт считает такие моменты как «problem results
     ignored»);
   - выражение восстановления проверяется только в состоянии PROBLEM, при
     режиме «recovery expression» и ложном основном выражении; лишь тогда
     важны его ошибки;
   - таймерные точки считаются, когда функции времени есть в основном
     выражении, либо в состоянии PROBLEM, когда они есть в выражении
     восстановления. Сетка таймера выровнена как на сервере
     (`30 * k + seed % 30`).
   Ошибки функций дают UNKNOWN и сохраняют предыдущее состояние, логика
   трёхзначная (`1 or UNKNOWN = 1`, `0 and UNKNOWN = 0`).

Нативный движок собран из релиза, указанного в `native/ZABBIX_TAG` (7.0.32).
Он проверен на живом сервере Zabbix 8.0 через `--compare-events`: у 23 из 24
триггеров с недельной историей все события воспроизведены с точностью до
секунды; оставшийся случай — разбиение значений по пачкам history syncer,
описанное ниже.

## Ограничения

- Не поддерживаются foreach/агрегатные функции с подстановочными ссылками
  (`/*/key`, `?[tag=...]`), глобальные регулярные выражения `@name`,
  строгий режим `nodata()` с окнами подавления прокси.
- В python-движке дополнительно отсутствуют `trendstl` (860 строк STL-разложения,
  есть только в native), `jsonpath`, `xmlpath`.
- Макросы, не раскрытые API (например, `{$MACRO}` без значения на хосте или
  любой макрос в произвольном выражении), нужно задавать через `--macro`,
  иначе вычисления будут UNKNOWN, и отчёт назовёт причину.
- Глубина проверки ограничена сроком хранения истории айтемов.
- Trend/baseline-функции сервер пересчитывает по своему часовому расписанию,
  тестер использует для них ту же 30-секундную сетку, поэтому такие переходы
  могут появиться раньше, чем на сервере (но не позже).
- Значения нескольких элементов с одинаковой меткой времени вычисляются один
  раз вместе. Сервер может разнести их по разным пачкам history syncer и
  пересчитать триггер дважды с неполным набором свежих значений; такие
  мгновенные «вспышки» по данным API не восстановить.
- Реальные события могут отличаться от модели из-за обслуживания,
  зависимостей, ручного закрытия, корреляции и правок триггера.
  `--compare-events` явно перечисляет такие расхождения.

## Разработка

```bash
uv sync
uv run pytest -q                                # тесты native пропускаются без библиотеки
TZ=UTC uv run python native/diff_test.py        # native против Python, ожидается "0 mismatches"
uvx ruff check src tests
```

CI (`.github/workflows/ci.yml`) гоняет тесты на Python 3.11–3.13 и отдельной
задачей собирает нативную библиотеку из закреплённого тега, требуя от
дифференциального теста 0 расхождений.
