# trigger-tester

[English](README.md) | Русский

Утилита проверяет триггер Zabbix 7.0+ на исторических данных: берёт выражение
триггера через API, находит айтемы, выгружает их историю (и тренды, если нужны)
за указанный период и прогоняет выражение в каждой точке времени так, как это
делал бы сервер. Результат — хронология смен состояния OK/PROBLEM и сводка.

## Установка

```bash
uv sync            # или: pip install -e .
uv run zbx-trigger-test --help
```

### Движок вычислений

Утилита умеет считать выражения двумя способами:

- **native** (рекомендуется): настоящий код сервера Zabbix (`libzbxeval` +
  `evalfunc.c`), собранный в `native/libzbxtester.so`. Операторы, трёхзначная
  логика UNKNOWN и все функции истории ведут себя байт в байт как на сервере.
  Сборка описана в [native/README.md](native/README.md); библиотека ищется по
  переменной `ZBX_TRIGGER_TESTER_LIB`, рядом с пакетом и в `native/`.
- **python**: встроенная реализация на Python, сверенная с кодом сервера
  функция за функцией (включая порт `prediction.c` для `forecast`/`timeleft`).
  Работает без сборки. Дифференциальный тест `native/diff_test.py` гоняет
  одни и те же кейсы через оба движка и должен показывать 0 расхождений;
  при смене тега Zabbix его стоит перезапустить.

По умолчанию (`--engine auto`) используется native, если библиотека найдена,
иначе python с предупреждением. Какой движок работал, видно в шапке отчёта.

## Использование

```bash
export ZABBIX_URL=https://zabbix.example.com
export ZABBIX_TOKEN=xxxxxxxx           # API token (или --user/--password)

# последние сутки
zbx-trigger-test -t 23456

# заданный интервал, сравнение с реальными событиями, подробный вывод
zbx-trigger-test -t 23456 --from "2026-11-01 00:00" --till "2026-11-02 00:00" \
    --compare-events -v

# прогнать другое выражение на тех же данных ("а что если")
zbx-trigger-test -t 23456 --period 7d \
    --expression 'min(/srv1/system.cpu.util,10m)>{$CPU.MAX}' --macro '{$CPU.MAX}=85'

# JSON для дальнейшей визуализации
zbx-trigger-test -t 23456 --json result.json
```

Основные параметры:

| параметр | назначение |
|---|---|
| `-t/--trigger` | ID триггера |
| `--from`, `--till`, `--period` | период: ISO-дата, unix time, `now-1d`, `now/d` |
| `--step` | шаг «таймерных» вычислений; `auto` = 30s, если есть `nodata()`, `now()`, `time()`, trend-функции или сдвиг времени |
| `--expression`, `--recovery-expression` | подменить выражения (синтаксис Zabbix, ссылки `/host/key`) |
| `--macro {$NAME}=VALUE` | значение пользовательского макроса, который API не раскрыл |
| `--initial-state` | состояние в начале периода; `auto` берёт последнее событие до периода |
| `--compare-events` | сравнить смоделированные смены состояния с событиями из Zabbix |
| `--json FILE` | полный результат (каждое вычисление, значения функций) |
| `--tz` | таймзона отображения и округления `now/d`; для native-движка переключает TZ процесса, укажите зону сервера Zabbix |
| `--engine` | `auto` / `native` / `python`, см. выше |

## Как это работает

1. `trigger.get` (с функциями, айтемами, хостами) и `trigger.get` с
   `expandExpression` — Zabbix сам раскрывает `{functionid}` и пользовательские
   макросы.
2. Выражение разбирается в AST с приоритетами операторов Zabbix
   (`-`, `not`, `* /`, `+ -`, `< <= > >=`, `= <>`, `and`, `or`), суффиксами
   `K M G T s m h d w`, строками и макросами.
3. Для каждого айтема считается, сколько истории нужно *до* начала периода
   (окна `5m`, `#N`, сдвиги `:now-1h`), и история выгружается `history.get`
   с пагинацией; для `trend*` — `trend.get`.
4. Точки вычисления — каждое новое значение любого айтема триггера в периоде
   плюс равномерная сетка `--step`. В каждой точке вычисляются выражение и
   recovery-выражение, прогоняется машина состояний с учётом
   `recovery_mode` и режима множественных событий. Ошибки функций дают
   UNKNOWN и сохраняют предыдущее состояние, логика трёхзначная
   (`1 or UNKNOWN = 1`, `0 and UNKNOWN = 0`).

## Ограничения

- Не поддерживаются foreach/агрегатные функции с подстановочными ссылками
  (`/*/key`, `?[tag=...]`), глобальные регулярные выражения `@name`,
  строгий режим `nodata()` с окнами подавления прокси.
- В python-движке дополнительно отсутствуют `trendstl` (860 строк STL-разложения,
  есть только в native), `jsonpath`, `xmlpath`.
- Макросы, не раскрытые API (например, `{$MACRO}` без значения на хосте),
  нужно задавать через `--macro`.
- Глубина проверки ограничена сроком хранения истории айтемов.
- Реальные события могут отличаться от модели из-за обслуживания,
  зависимостей, ручного закрытия, изменений триггера.
